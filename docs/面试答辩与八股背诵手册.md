# 【模块一】项目全景速写（三版）

## 版本1｜30 秒电梯版（场景："简单介绍一下你的项目"）

> 独立实现星载Agent可信监护框架：故障注入、双监护、三级路由、前置门控。核心决策：监护与被监护隔离——墙钟看门狗补死区，工具执行前持一次性许可。149测试全绿。

- 背诵要点：定位一句 + **一个决策**（隔离）+ **一个机制**（许可）+ **一个数字**（149）
- 结构核对：定位✓ 职责✓ 决策✓ 定性结果✓；只字不提功能清单
- 字数：约 80 字（若要求严格 ≤80，删"三级路由"或"149"二选一）
- **技术信号**：我会讲取舍，不会背功能列表。

## 版本2｜1 分钟标准版（场景："详细讲讲这个项目"）

> 【痛点】星上 Agent 做故障诊断与任务重规划，但 Agent 不可信——可能死锁、误诊、越权执行。【角色】我独立完成五模块框架：故障注入测试床、RSM/DTM 双监护、Gateway 汇合判定、EGM 执行门控。【方案】三个决策：①非侵入式注入——选**运行时替换 + 配置驱动**而非改 Agent 源码，保证被测的就是生产代码；②墙钟看门狗——事件驱动监护在"崩溃后无事件可看"时永久死等，看门狗靠墙钟主动推超时，并以 **CPU 特征**区分忙等死循环与无输出挂起；③执行前置门控——旧链路是"跑完再事后判定"，零拦截力，我把裁决前移到工具执行前，mutation 工具必须持一次性许可。【结果】149 项测试、9 类故障检测率 100%、CI 四矩阵全绿。【反思】它是地面验证原型，进程隔离、许可持久化、资源预算是已知边界。

- **技术信号**：两个"选 A 不选 B"（运行时替换 vs 改源码；墙钟 vs 事件驱动）+ 一个架构演进（事后→前置）+ 主动亮边界。

## 版本3｜3 分钟深挖版（场景："这个模块展开说说"）

按"问题→约束→方案对比→选型→实现→代价→反思"给 4 条决策链：

**决策链 1：监护死区 → 墙钟看门狗 + CPU 判别**
- 问题：事件驱动监护靠"新事件触发检查"，Agent 崩溃后事件流断掉 → 超时判定永不触发（证据：rsm/monitor.py:_watchdog_loop 注释）
- 方案对比：A 事件驱动（死区）/ B 独立看门狗线程 + 墙钟推进
- 选 B。实现：0.1s 轮询三类超时；工具挂起按最近 CPU 采样判别——忙等(≥50%)=INFINITE_LOOP，阻塞=NO_OUTPUT_TIMEOUT（证据：rsm/monitor.py:start_watchdog、:290；rsm/detectors/__init__.py:ToolTimeoutMonitor._discriminate）
- 代价：轮询开销 + 判别误分类风险；换来看门狗与被监护者零依赖

**决策链 2：事后门控零拦截力 → 执行前置门控**
- 问题：旧链路 Agent 跑完全部工具，Gateway/EGM 才判定——门控只审计、不拦截
- 方案对比：A 事后模拟（现状）/ B 工具执行前同步裁决
- 选 B。实现：实时事件总线喂 RSM/DTM/Gate（证据：five_module_orchestrator.py:LiveEventCapture），mutation 工具在 `_wrap_tool_call` 里先 `authorize` 再执行（证据：agent/task_agent.py:_wrap_tool_call、egm/gate.py:ExecutionGate.authorize）；BLOCK/SUSPEND 拒绝，仅 PERMIT 由 EGM 签发一次性许可，`consume` 消费即失效（证据：egm/gate.py:ExecutionGate.consume）
- 代价：同步阻塞工具线程；门控是 Agent 层"自律"，强制执行需下沉执行器侧【代码中未体现】

**决策链 3：检测结果被覆盖 → 累积式结果**
- 问题：每事件新建结果对象，历史检出被"最后一个事件"覆盖（实测踩坑：检查器全触发但 get_last_result 返回 0 issue）
- 方案对比：A 逐事件快照 / B 单例累积 + 同源去重
- 选 B。实现：`_cumulative_result` 持续追加，`add_issue` 对同检测器同类型去重（证据：rsm/monitor.py:_cumulative_result、dtm/monitor.py:_cumulative_result）
- 代价：issues 无界增长（长跑需窗口裁剪【未实现】）

**决策链 4：检测率自证 → GT 隔离 + 逐故障匹配**
- 问题：第一版 benchmark 故障没真注入（空转），报出假 100%；复合故障 OR 口径会掩盖"只检出一个也算成功"
- 方案对比：A 注入器不接 Agent / 接了；A' OR 口径 / 逐故障匹配
- 选"真注入 + 逐故障匹配"。实现：GroundTruthLogger 只落本地文件不上事件总线（证据：fault_injector/injector.py:GroundTruthLogger）；benchmark 显式创建 injector 传入 TaskAgent，标签映射逐故障核对（证据：experiments/run_benchmark.py:FAULT_TO_DETECTION_LABEL）
- 代价：口径更严 → 会暴露漏检（这正是目的）

- **技术信号**：每条链都有"问题—对比—代价"，且全部指向"我踩过坑并修掉了"——这是可验证的工程素养。

# 【模块二】STAR 拆解

## S（情境）
- 业务场景：星载 Agent（故障诊断、任务重规划）辅助地面操作员决策，**严守"辅助决策、人最终裁决"的安全边界**
- 技术约束：可信监护要求**可检测、可裁决、可追溯**；验证必须**可复现**；零第三方依赖（星载不可 pip）
- 定位：**地面研究原型**——无真实在轨环境与真 LLM Agent【代码中未体现，README 已声明】

## T（任务）
- 我负责：故障注入测试床 + RSM/DTM 双监护 + 执行前置门控 + 量化验证体系

- 交付标准：故障场景可复现、检测结果可验证、数字不造假

# 【模块三】技术栈五层拆解（14 张战术卡片）

## 卡片1｜装饰器 + 运行时替换（Decorator & Monkey-patching）
- L1 是什么：不改源码的插桩手段。位置（证据：injector.py:inject_execution；task_agent.py 构造器替换 tool_registry.call）
- L2 怎么运作：闭包包函数，调用前后插逻辑；运行时把方法引用替换成 wrapper。结构：wrapper 栈 + functools.WRAPPER_ASSIGNMENTS
- L3 为什么：替代①改源码插桩（侵入）②子类化（需预埋 hook）；选它因为"配置驱动开关"必须运行时生效；代价是只能函数边界注入
- L4 追问：①"装饰器不是更优雅吗？"→装饰器类定义时生效，无法按 config 运行时开关。②"wraps 不写会怎样？"→__name__ 全变 wrapper，日志失去辨识。③"还能更解耦吗？"→可改事件回调列表，避免 wrapper 嵌套
- L5 优化：注入点超过 10 个再上回调列表；现在不值得

## 卡片2｜多线程守护模型（Daemon Threads + Lock/Event）
- L1 是什么：4 个 daemon 线程（心跳/遥测/资源采样/看门狗）+ 主执行线程。位置（证据：task_agent.py:303/320/351；rsm/monitor.py:start_watchdog）
- L2 怎么运作：sleep 节奏 + `while self._running` 停机；Lock 护共享计数与日志；Event 停看门狗。GIL 下 CPU 密集不并行，但本项目线程主体是等待密集
- L3 为什么：替代①asyncio（单线程卡死=全体卡死、await 传染）②多进程（失去共享便利）；选线程为模拟"两个独立生命周期"；代价是调度不可控
- L4 追问：①"GIL 饿死心跳？"→eval-breaker 每 ~5ms 让出，只延迟一个片。②"为什么 daemon？"→进程退出即回收，不留僵尸。③"为什么不 join？"→挂起类故障下 join 会卡死，正是超时护栏存在的理由
- L5 优化：节奏器换 condition 定时；当前够用

## 卡片3｜墙钟看门狗 + CPU 特征判别（Wall-Clock Watchdog）
- L1 是什么：不依赖事件流、按墙钟主动推超时的独立监护线程。位置（证据：rsm/monitor.py:_watchdog_loop）
- L2 怎么运作：0.1s 轮询三类超时（心跳/工具挂起/停滞）；工具挂起按最近 cpu 采样分叉（≥50% 忙等 / <50% 阻塞）；shutdown 事件带原因区分正常停机
- L3 为什么：替代①纯事件驱动（死区）②外部硬件看门狗【未实现】；选线程折中；代价：轮询空转 + 阈值启发式
- L4 追问：①"死区是什么？"→崩后无事件，靠事件触发的检查永不执行。②"50% 哪来的？"→工程启发式，可配置。③"看门狗自己挂了？"→没有看门狗的看门狗，生产需硬件级
- L5 优化：采样中位数防抖、条件变量省轮询；值得做但非优先

## 卡片4｜累积式检测结果（Cumulative Results）
- L1 是什么：检测结果单例累积、不被后续事件覆盖。位置（证据：rsm/monitor.py:_cumulative_result；dtm/monitor.py:_cumulative_result）
- L2 怎么运作：首次 process_event 建单例，后续只 add_issue；同检测器同类型去重；get_last_result 返回累积态
- L3 为什么：替代①每事件新建结果（历史被覆盖——实测踩坑）②调用方自己聚合（责任外溢）；代价：issues 无界增长
- L4 追问：①"为什么 Gateway 不逐事件消费？"→裁决需要"迄今发生过什么"而非"最后一个事件"。②"去重会不会漏报？"→键是(检测器,类型)，不同 call_id 的同类事件不重复计。③"内存会涨多少？"→单次运行 issue 数个，长跑需裁剪
- L5 优化：加窗口裁剪；低优先

## 卡片5｜结构化事件流 + 观察者总线（Event Stream & Observer Bus）
- L1 是什么：11 类 JSON 事件 + 内存 list 总线 + 实时 fan-out。位置（证据：task_agent.py:_log_event；five_module_orchestrator.py:LiveEventCapture）
- L2 怎么运作：_log_event 注入 run_id/global_seq/schema_version；publish 缓存 + 投递 RSM/DTM/Gate 三观察者；call_id 配对 tool_call/result
- L3 为什么：替代①直接对象调用（耦合）②消息队列/Redis【README 声明后续】；选内存总线因为单进程验证够用；代价：无背压、无持久化
- L4 追问：①"global_seq 干嘛的？"→跨总线迁移后的乱序检测预留。②"事件丢了？"→进程内不丢；跨进程要重排+丢包检测【未实现】。③"为什么 JSON？"→可读可审计，上星可换二进制帧
- L5 优化：有界队列+背压+采样；换总线只改 LiveEventCapture

## 卡片6｜哈希证据绑定 + Ground Truth 隔离（Hash Binding & GT Isolation）
- L1 是什么：遥测 SHA256 绑定结论↔证据；GT 只落盘不上总线。位置（证据：agent/telemetry.py:get_telemetry_hash；injector.py:GroundTruthLogger；egm/gate.py:binding_digest_for）
- L2 怎么运作：sort_keys 保证确定性；GT 追加写 JSONL + Lock；许可绑定摘要防挪用
- L3 为什么：替代①GT 走总线（自证）②明文比对；选哈希因为低成本防意外篡改；代价：截断 16hex 不防恶意
- L4 追问：①"截断 64bit 够吗？"→防误碰够，防对抗不够，生产要 HMAC。②"sort_keys 为什么重要？"→同内容同哈希，跨模块重算可比。③"GT 谁写？"→注入器写，监护器读不到——评估公正性的根基
- L5 优化：全量摘要 + HMAC；原型阶段不需要

## 卡片7｜一次性许可状态机 + 执行前置门控（One-Time Permit & Pre-Gating）
- L1 是什么：8 态 EGM + 工具执行前的许可裁决。位置（证据：egm/egm.py:EGMState、Permit；egm/gate.py:ExecutionGate.authorize/consume）
- L2 怎么运作：authorize→Gateway 裁决→PERMIT 才签发→执行→consume（used 标记+binding 校验+expiry）；BLOCK/SUSPEND 自动态一律拒
- L3 为什么：替代①事后模拟（零拦截）②执行器侧强制【未实现】；选 Agent 层自律门控（防"不可信"不防"恶意"）；代价：同步阻塞 + 可绕过
- L4 追问：①"SUSPEND 为什么不给人审批机会？"→自动态不替人决定；审批在事后复核模拟。②"重启许可就没了？"→内存态是原型边界。③"gate 抛异常？"→冒泡→任务 failed（fail-closed）
- L5 优化：许可持久化、执行器侧强制；这俩是"下一步"最有分量的两件事

## 卡片8｜三级路由 + 增量物理约束（Priority Routing & Incremental Constraints）
- L1 是什么：BLOCK>SUSPEND>PERMIT 短路裁决 + 动作功率/热投影。位置（证据：gateway/gateway.py:decide、:274-306）
- L2 怎么运作：RSM critical→BLOCK；trust<0.5→BLOCK；RSM 故障/trust<0.8/物理违规→SUSPEND；requires_approval/不可逆变异→SUSPEND；全过→PERMIT。增量投影：当前功耗+power_delta 与 发电×0.95 比
- L3 为什么：替代①只看当前快照（拦不住"即将越界"）②Agent 自检（会被误导）；选外部独立裁决；代价：投影是线性近似
- L4 追问：①"阈值哪来的？"→演示参数，未对齐任务书。②"功率可线性叠加？"→真实有瞬态尖峰，需阶跃模型。③"RSM 和 DTM 冲突听谁？"→严重度优先级短路，全部进 reasons 审计
- L5 优化：阈值出处文档化 + 阶跃模型；低成本高信用

## 卡片9｜可信度量化（Trust Scoring）
- L1 是什么：trust_score 加性扣分 + risk_label 分档。位置（证据：dtm/monitor.py:add_issue；dtm/checkers/__init__.py 四检查器）
- L2 怎么运作：四检查器各出 penalty(0.2/0.25/0.3/0.35)→1.0 递减→label 分档；NO_FAULT 跳过校准/完整性
- L3 为什么：替代①乘积式（不可解释）②布尔判定（无梯度）；选加性因为可解释可叠加；代价：权重无校准
- L4 追问：①"0.3 怎么来的？"→严重度主观排序，未校准——诚实讲。②"两个检查器同时报怎么办？"→各自扣分叠加，单调下降。③"会负分吗？"→clamp 到 0
- L5 优化：用注入实验 FP/FN 反推权重；方法论加分项

## 卡片10｜滑动窗口趋势 + 连续计数（Sliding Window & Consecutive Count）
- L1 是什么：内存泄漏/重复调用的过程性检测。位置（证据：detectors:MemoryMonitor、RepetitiveCallMonitor）
- L2 怎么运作：绝对阈值 OR 窗口内单调增长>50MB；连续同工具≥4 次触发，异工具重置
- L3 为什么：替代①只看瞬时值（误报）②只看绝对阈值（漏报慢泄漏）；组合判据覆盖两类；代价：窗口参数与采样周期耦合
- L4 追问：①"窗口 5 怎么选？"→采样 1s×5、注入步长 50MB 匹配。②"单调增长会不会误报正常增长？"→叠加"累计>50MB"阈值过滤。③"重复调用 4 次哪来的？"→与注入预设对齐，参数联动
- L5 优化：差值累积替代全窗口扫描；低优先

## 卡片11｜遥测噪声建模（Noise Modeling）
- L1 是什么：4 种可叠加传感器噪声。位置（证据：agent/noise_model.py:NoiseModel、_apply_gaussian、_apply_spike、should_drop_packet）
- L2 怎么运作：高斯（相对 σ）/漂移（per-key 累积器）/脉冲（瞬时、下帧消失）/丢包（帧级）；噪声是激励源
- L3 为什么：替代①无噪声（温室测试）②真实在轨数据【没有】；选合成噪声验证监护器鲁棒性；代价：相对 σ 对跨量级小值失真
- L4 追问：①"噪声和故障注入区别？"→连续概率扰动 vs 离散确定性行为异常。②"collision_risk=1e-6 用相对 σ？"→已知边界，应按量级分桶。③"heavy 噪声误报率 100% 正常吗？"→重噪本应视为异常，README 有诚实披露
- L5 优化：绝对+相对混合噪声；中优先

## 卡片12｜零依赖跨平台系统观测（Zero-Dep OS Telemetry）
- L1 是什么：不装 psutil 自己取 RSS 与 CPU。位置（证据：task_agent.py:_get_memory_mb、_resource_loop）

## 卡片13｜试验隔离 + 超时护栏（Trial Isolation & Timeout Fencing）
- L1 是什么：每 trial 独立初始状态 + join 超时兜底。位置（证据：run_benchmark.py（join 3s、内存释放、reset）；five_module_orchestrator.py（join 5s））

- L4 追问：①"超时后线程还在跑？"→忙等循环检查 _running，stop 即退。②"清理清单怎么定的？"→每条对应一个踩过的坑。③"为什么 3s？"→正常 trial 0.5s，3s 是 6 倍裕度

# 【模块四】架构灵魂五问

## 分层图

```
实验编排层 main / orchestrator / five_module_orchestrator（LiveEventCapture 总线、超时护栏）
被测对象层 agent/（确定性6步循环 + 噪声模型 + 规则诊断 + 工具清单）
注入验证层 fault_injector/（装饰器+运行时替换+强度预设+GT隔离）
事件契约层 11类结构化事件（run_id/global_seq/call_id）
监护层     rsm/（5检测器+墙钟看门狗+CPU判别+累积） dtm/（4检查器+trust+累积）
裁决层     gateway/（C1-C5绝对+增量、三级路由）
门控层     egm/（8态机+一次性许可） + egm/gate.py（前置门控）
数据层     logs/*.jsonl（GT与审计，文件单向）
工程层     tests/ experiments/ dashboard/ CI
```

## Q1 为什么选这个架构？换一种会怎样？
- 要点：核心是**事件契约解耦**——五模块只认事件不认对象，这是"监护与被监护可分离"的前提。换微服务：部署复杂，研究原型收益为零；换线程池处理事件：会丢失事件时序与累积语义（监护判定依赖顺序）。
- 可能追问："这不就是单体吗？"→ 是，但**边界按模块分、通信按事件**，单体内已具备拆开的接口条件。
- 防御话术："这个架构的取舍是：用单进程牺牲隔离真实性，换协议验证的可复现性——隔离性我明确列为下一步。"

## Q2 数据量/事件量暴增 100 倍，哪个模块先崩？
- 要点：**事件总线**（events 列表无界 append，benchmark 单 trial 131 事件，×100×长跑 → 内存线性涨）+ RSM 全量回放循环 O(events)。其次 GT/审计 JSONL 只追加不轮转。
- 预防：有界队列 + 背压 + 事件采样（监护层可降频）+ 日志轮转。
- 追问："背压会丢事件，监护不就不准了？"→ 丢包本身要作为事件（packet_loss 已有先例），监护对丢包要 fail-safe（宁 SUSPEND 不 PERMIT）。
- 防御："我在设计里预留了 global_seq 做乱序/丢失检测，背压策略是明确的下一步。"

## Q3 核心依赖不可用，如何降级？
- 要点：核心依赖=事件总线（进程内，理论不宕）。**没有跨进程降级设计**【代码中未体现】——如实说。已有的是：GT 写失败会抛异常（无重试）；看门狗内部异常被吞（`except: pass`，静默）。
- 追问："看门狗吞异常不是更危险？"→ 是，演示取舍；生产要告警通道。
- 防御："降级矩阵我没有做，但我知道该做什么：监护侧 fail-safe（观测缺失=SUSPEND）、审计写失败进告警队列。"

## Q4 模块间耦合方式？替换一个模块要改哪里？
- 要点：三种耦合——**异步事件回调**（Agent↔监护器）、**同步函数调用**（监护器→Gateway→EGM）、**单向文件**（GT/审计）。替换成本表：换事件总线只改 LiveEventCapture；换 DTM 要小心 trust 回退 1.0 是 fail-open；移除 Gate 门控归零。
- 追问："fail-open 你意识到了吗？"→ 意识到：缺失观测时裁决偏向放行，这是当前设计的一个已知风险点，正确方向是 fail-safe。
- 防御："我按'接口最小化'设计，每个模块对外只有一个入口函数（process_event / decide / authorize）。"

## Q5 最大的技术债？三个月重构先动哪？
- 要点：**债单**：①单进程监护（隔离真实性）②自律门控（可绕过）③许可内存态 ④参数无出处 ⑤事件总线无背压。三个月顺序：第 1 月进程隔离（看门狗独立进程 + IPC 总线）→ 第 2 月执行器侧强制门控 + 许可持久化 → 第 3 月参数标定 + 系统级性能测量。
- 追问："为什么进程隔离排第一？"→ 它是"监护有效性"的根基，其他都是增强。
- 防御："我知道债在哪、也知道偿还顺序——这比没有债更重要。"
